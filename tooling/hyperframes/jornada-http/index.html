Maria quer se inscrever no curso Fullstack. Ela digita o endereço no navegador.
A internet não entende nomes. O DNS é uma agenda: troca o nome do site pelo IP, o endereço do servidor.
O navegador envia uma requisição: GET “me dá a página”. Ela viaja até o servidor web.
O servidor devolve uma resposta: 200 OK + três arquivos: HTML, CSS e JavaScript.
Atenção: o frontend não roda no servidor. Ele roda aqui, no navegador da Maria.
Maria preenche o formulário e clica em “Quero me inscrever”.
O frontend só mostra telas. Ele não sabe se ainda tem vaga e não guarda inscrições.
Tudo que roda no navegador, a Maria pode abrir e alterar (F12). Por isso as regras ficam no servidor.
Para cadastrar, o frontend faz outra requisição, agora para a API. Veja o que vai dentro dela:
Endpoint = método + endereço. É a “porta” da API que faz UMA coisa: aqui, criar uma inscrição.
A API confere as regras… tudo certo! Mas onde ficam as inscrições? A API não guarda dados.
Quem guarda é o banco de dados: um PostgreSQL rodando dentro de um container Docker.
O banco grava a linha e devolve o número gerado: id 42. Com o banco, a API não fala HTTP: fala SQL.
Agora a API monta a resposta. Toda requisição volta como resposta: status + corpo.
A resposta volta pelo mesmo caminho. O frontend lê o status e mostra a tela certa.
Resumo: GET ➜ 200 no fluxo 2. POST ➜ 201 agora. Pedido e resposta, sempre em par.
E quando o pedido vem errado? João esqueceu o e-mail e clicou em inscrever.
A API confere a primeira regra: e-mail vazio! Ela recusa antes de chegar ao banco.
400 Bad Request: o pedido precisa ser corrigido. O front mostra a mensagem; a API decide.
