01

DTO: o formulário da recepção

Por que a API não deveria receber a entidade inteira.

🏥 A recepção da clínica

Na clínica, você não entra na sala de arquivos para escrever no seu prontuário. Você preenche o formulário da recepção: nome, telefone, convênio. Não existe campo para “número do prontuário”: quem decide é a clínica. Lá dentro, uma pessoa copia os dados do formulário para o prontuário. Na saída, você recebe um comprovante, com coisas que você nunca escreveu: o número do atendimento, a data e a hora.

Onde a analogia para: o formulário não é uma tranca de segurança. Ele só define quais campos existem. Se algo não tem campo no formulário, não entra. Mas o que tem campo ainda pode vir errado; para isso existe a validação, no Encontro B.

O nome técnico

DTO significa Data Transfer Object, ou objeto de transferência de dados. É uma classe que só carrega os dados que atravessam a fronteira HTTP, em uma direção. Não tem regra de negócio e não vai para o banco. Na clínica, o formulário e o comprovante são DTOs; o prontuário é a entidade.

JSON que chega→ProdutoRequestDTOo formulário→Mappercopia os campos→Produtoa entidade→🐘 banco
JSON que sai←ProdutoResponseDTOo comprovante←Mapper←Produto←🐘 banco

São dois DTOs, um para cada direção. O de entrada diz o que o cliente da API pode mandar. O de saída diz o que a API mostra. A entidade continua existindo, mas agora fica do lado de dentro, conversando só com o banco.

Nosso Produto terá estes campos (os mesmos do GestorPRO que você construiu no React, mais um campo novo, criadoEm, a data e hora do cadastro):

02

record: um DTO em poucas linhas

Uma classe que só carrega dados, escrita pelo próprio Java.

No Cap 11 você escreveu classes com campos privados, construtor e getters. Um DTO só precisa disso: guardar dados e deixar ler. Veja como ficaria um DTO com apenas dois campos, escrito do jeito que você já conhece:

public class ProdutoRequestDTO { private final String nome; private final BigDecimal preco; public ProdutoRequestDTO(String nome, BigDecimal preco) { this.nome = nome; this.preco = preco; } public String getNome() { return nome; } public BigDecimal getPreco() { return preco; } }

Dezessete linhas para dois campos. Com quatro campos, seriam mais de trinta, todas previsíveis. O Java 16 trouxe uma forma curta para esse caso exato: o record.

public record ProdutoRequestDTO(String nome, BigDecimal preco) { }

Leia assim: “um registro de dados com nome e preco”. Entre parênteses ficam os componentes do record. A partir deles, o Java gera sozinho os campos privados e final, o construtor com os dois valores, os métodos de leitura e alguns métodos auxiliares que você ainda não precisa.

Três diferenças que pegam iniciantes

1 · Ler sem “get”

O método de leitura tem o mesmo nome do componente: dto.nome(), e não dto.getNome().

2 · Sem setter

O record nasce pronto e não muda. Não existe setNome. Para um formulário recebido, é exatamente o que queremos.

3 · Só para DTO

A entidade continua com Lombok: o JPA precisa de construtor vazio e de alterar campos. Record é ótimo para DTO e ruim para entidade.

Os campos são final, como no Service do Cap 12: recebem valor uma vez, no construtor. Isso combina com a ideia de formulário: depois de entregue, ninguém rabisca.

04

Dinheiro não é double

Um experimento de 10 segundos que você já sabe fazer.

Abra o console do navegador com F12 (aba Console), como no Cap 2, e digite:

0.1 + 0.2 0.30000000000000004

Não é um bug do JavaScript. No Java acontece exatamente o mesmo: System.out.println(0.1 + 0.2); num main do Cap 11 imprime 0.30000000000000004. O computador guarda números com vírgula em binário, e alguns decimais simples não têm representação exata em binário, assim como 1/3 não tem em decimal (0,3333…). O double guarda uma aproximação muito boa, mas aproximação.

Para medir temperatura, isso não importa. Para dinheiro, importa: somando milhares de vendas, centavos aparecem ou somem, e o relatório não bate com o caixa.

BigDecimal: decimal exato

O Java tem uma classe para isso: BigDecimal, do pacote java.math. Ela guarda o número em decimal, do jeito que escrevemos. Um teste rápido, se quiser rodar num main do Cap 11:

System.out.println(0.1 + 0.2); System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2"))); System.out.println(new BigDecimal(0.1)); 0.30000000000000004 0.3 0.1000000000000000055511151231257827021181583404541015625

Repare na terceira linha. Criar um BigDecimal a partir de 0.1 (um double) copia a aproximação inteira. Quando criar à mão, use texto: new BigDecimal("0.1"). Na nossa API isso quase não aparece: o Spring converte o número do JSON direto para BigDecimal, sem passar por double.

No JSON, nada muda: o preço continua sendo um número, "preco": 320.00. No banco, vamos pedir uma coluna decimal com tamanho definido:

@Column(precision = 10, scale = 2)
AtributoSignificaNo nosso caso
precision = 10Quantos dígitos no total.Até 10 dígitos.
scale = 2Quantos desses ficam depois da vírgula.Sempre 2 casas: centavos.

Resultado: o maior preço possível é 99.999.999,99. No PostgreSQL, a coluna aparece como numeric(10,2).

Passo 4 · Mapper: o tradutor

Alguém precisa copiar os dados do formulário para a entidade e da entidade para o comprovante. Poderíamos fazer isso dentro do Service, mas a cópia vai se repetir em vários endpoints. Ela ganha uma classe própria. Crie o pacote mapper e a classe ProdutoMapper:

  • toEntity (“para entidade”) cria um Produto vazio e copia os quatro campos do formulário. Repare no que não é copiado: id e criadoEm. Não existe de onde copiar.
  • toResponse (“para resposta”) monta o comprovante com new ProdutoResponseDTO(...). Os valores vão na mesma ordem dos componentes do record.
  • static, como você viu no Cap 11: o método pertence à classe. Chamamos ProdutoMapper.toEntity(dto) sem fazer new ProdutoMapper(). O Mapper não guarda nada; ele só traduz.

Passo 5 · Service: cadastrar

O método cadastrar tem quatro linhas, uma por tarefa: traduzir o formulário em entidade; carimbar a data com o relógio do servidor (LocalDateTime.now()); salvar (o save devolve a entidade já com o ID gerado); e traduzir de volta para o comprovante. A data é uma regra do servidor, por isso mora no Service, e não no Mapper.

R · Listar: a esteira

Converter uma lista inteira, e a primeira lambda do backend.

GEThttp://localhost:8080/produtos200 OK

O repository.findAll() devolve uma List<Produto>: entidades. Mas o Controller só fala DTO. Precisamos transformar cada Produto em um ProdutoResponseDTO e juntar tudo numa lista nova. Primeiro, do jeito que você já sabe, com for:

public List listar() { List produtos = repository.findAll(); List respostas = new ArrayList<>(); for (Produto produto : produtos) { respostas.add(ProdutoMapper.toResponse(produto)); } return respostas; }

Funciona. Mas “pegar cada item, transformar e juntar numa lista nova” é tão comum que existe uma forma curta para isso. Você já usou essa ideia no Cap 5, no React:

const nomes = produtos.map(produto => produto.nome);

Em Java, a mesma ideia fica assim:

produtos.stream() .map(produto -> ProdutoMapper.toResponse(produto)) .toList();

🏭 A esteira

stream() liga a esteira e coloca os produtos nela, um atrás do outro. map(...) é uma estação de trabalho: cada produto que passa entra como entidade e sai como comprovante. toList() é a caixa no fim da esteira, que junta tudo numa lista nova. A lista original não muda.

Como ler produto -> ProdutoMapper.toResponse(produto)

Isso é uma lambda: uma função curta, sem nome, escrita no lugar onde é usada. É a mesma ideia da arrow function do Cap 2. À esquerda da seta, o parâmetro: o item que está passando (chamamos de produto, mas o nome é escolha sua). À direita, o corpo: o que fazer com ele. O resultado do corpo é devolvido automaticamente, sem return.

JavaScriptproduto => ...igual + maior
Javaproduto -> ...hífen + maior
⚠️ A seta do Java são dois caracteres: - seguido de >. O IntelliJ e o VS Code costumam desenhar os dois juntos como uma seta só (→), por causa de uma fonte com “ligaduras”. É só desenho: digite hífen e sinal de maior. Se você copiar uma seta → de algum lugar, o Java responde illegal character: '\u2192'. E se escrever a seta do JavaScript (=>), responde illegal start of expression.

R · Buscar: o 404 de verdade

Abrir a caixa e reagir quando ela vem vazia.

GEThttp://localhost:8080/produtos/{id}200 OK · 404 Not Found

No Cap 12, o findById devolvia um Optional: uma caixa de presente que pode vir com o fornecedor dentro ou vazia. O Controller devolvia a caixa fechada, e a caixa vazia virava 200 com null. Para quem chamou, “deu certo, mas não veio nada” é uma resposta confusa.

O status certo para “isso não existe” é 404 Not Found, que você conheceu na Parte 0 do Cap 12. Agora vamos abrir a caixa no Service e reagir:

Produto produto = repository.findById(id) .orElseThrow(() -> new ResponseStatusException( HttpStatus.NOT_FOUND, "Produto não encontrado"));
  • orElseThrow quer dizer “me dê o que está na caixa; ou então, se estiver vazia, lance este erro”. Caixa cheia: a variável produto recebe o produto. Caixa vazia: o erro é lançado.
  • ResponseStatusException é uma exceção que já carrega o status HTTP da resposta. O Spring a reconhece e responde 404 sozinho.
  • throw (lançar) interrompe o método no meio. As linhas de baixo, inclusive o return, nem chegam a executar.
  • () -> new ResponseStatusException(...) é outra lambda, agora sem parâmetro: os parênteses ficam vazios. Ela é uma receita para criar o erro, e só é executada se a caixa estiver vazia.

Passo 1 · Service: buscar

Três imports novos: HttpStatus, ResponseStatusException e, no Controller, PathVariable. Use Alt+Enter no IntelliJ quando um nome ficar vermelho, mas confira se o pacote importado é o mesmo do código acima.

Passo 2 · Controller: buscar

O método devolve ProdutoResponseDTO, não mais um Optional. Quando chega ao return, o produto com certeza existe; se não existisse, o Service já teria lançado o 404.

Passo 3 · Testar os dois caminhos

O status está certo. Mas repare: a mensagem “Produto não encontrado” que escrevemos não aparece. Por padrão, o Spring esconde mensagens de erro da resposta. Vamos ligar isso de propósito na seção 11, junto com as mensagens de validação.

U · Atualizar sem perder nada

Buscar antes de mexer, e não repetir código.

PUThttp://localhost:8080/produtos/{id}200 OK · 404 Not Found

No Cap 12, o PUT fazia fornecedor.setId(id) e save: montava um objeto novo com os dados do JSON e gravava por cima. Pense no que isso faria com o Produto. O JSON do PUT não tem criadoEm (nem pode ter: o DTO não deixa). O objeto novo chegaria com a data vazia, e o banco recusaria, porque a coluna é NOT NULL. E, se a coluna aceitasse vazio, a data do cadastro original seria apagada.

O jeito certo tem três passos: buscar o produto que já existe (404 se não houver), copiar para ele só os campos do formulário, e salvar. O que o formulário não tem, como id e criadoEm, fica como estava.
