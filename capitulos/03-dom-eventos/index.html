A ponte: HTML + JS finalmente se falando
Saindo do Console, entrando na página

No Cap 1 você montou a estrutura (HTML). No Cap 2 você aprendeu a lógica (JavaScript), mas tudo aparecia só no console.log. Funcionava… só que ninguém vê o Console no dia a dia.

🎭 O roteiro e o palco

Pense no HTML como o palco montado: cenário, objetos, atores parados. O JavaScript é o diretor que entra, aponta para um ator ("você!"), e manda ele fazer algo ("levante a placa!"). Neste capítulo o JS sai dos bastidores (Console) e dirige o palco (a página).

Para o diretor dirigir, ele precisa de duas coisas: enxergar os atores (o DOM) e achar o ator certo (os seletores). Vamos por partes.

🌳
O DOM: sua página virou uma árvore
A ponte que o navegador monta entre o HTML e o JS
🌳 Uma árvore genealógica da página

Quando o navegador lê seu HTML, ele não guarda um texto: ele monta uma árvore de objetos vivos — um para cada tag. O <body> é o tronco; dentro dele nascem os galhos (<h1>, <ul>), e dos galhos saem as folhas (<li>). Essa árvore tem um nome: DOM (Document Object Model). É ela que o JavaScript consegue pegar e mexer.

Aperte montar a árvore e veja o mesmo HTML virar nós. Passe o mouse (ou clique) num nó para ver a tag correspondente acender 👇

💡 A palavra mágica: document

O JavaScript já vem com uma variável pronta chamada document — é a porta de entrada para essa árvore. Tudo que você vai fazer com a página começa em document.algumaCoisa.

🎯
Selecionar: apontar para um elemento
document.querySelector — achar o ator certo
🎯 "Você, de camiseta vermelha!"

Antes de mandar alguém fazer algo, o diretor precisa apontar para a pessoa certa. No DOM, apontar é selecionar. E você aponta usando os mesmos endereços que já aprendeu no CSS: #id para um elemento único e .classe para um grupo.

selecionar.jsJavaScript
// querySelector pega o PRIMEIRO que casar com o endereço
const titulo = document.querySelector("#titulo");  // pelo id
const primeiroItem = document.querySelector(".item"); // pela classe

// querySelectorAll pega TODOS numa lista
const itens = document.querySelectorAll(".item");

console.log(titulo);      // o elemento <h1>
console.log(itens.length); // quantos casaram

Escolha um endereço e veja o que ele seleciona na página de mentira. Repare no que acontece com .preco (que não existe ali) 👇

Mudar a página: agora o JS escreve na tela
textContent, style e classList

Selecionou o elemento? Agora é só dar ordens a ele. As três ordens que você mais vai usar:

mudar.jsJavaScript
const titulo = document.querySelector("#titulo");

// 1) trocar o TEXTO de dentro
titulo.textContent = "Bem-vindo!";

// 2) mudar o ESTILO (CSS pelo JS)
titulo.style.color = "crimson";

// 3) ligar/desligar uma CLASSE do CSS
titulo.classList.add("destaque");
🧠
textContent troca só o texto, com segurança. Existe também o innerHTML, que aceita tags HTML dentro — poderoso, mas perigoso (BugZilla explica). Comece pelo textContent; ele resolve 90% dos casos.
💡 Por que classList é tão usado?

Em vez de empilhar .style.cor, .style.fundo, .style.borda no JS, você cria uma classe bonita no CSS (ex.: .destaque) e só liga ela com classList.add("destaque") ou alterna com classList.toggle("destaque"). CSS cuida da aparência, JS cuida de quando. Cada um no seu quadrado.

Eventos: reagir ao que o usuário faz
addEventListener — o JS fica "de ouvido em pé"
🔔 A campainha da casa

Você não fica encarando a porta o dia todo esperando visita. Você instala uma campainha: quando alguém aperta, ela te avisa e aí você age. Um evento é isso — o clique é a campainha tocando, e o addEventListener é você dizendo "quando tocar, faça isto".

⌨️
Vem aí a arrow function () => { } que você viu no Cap 2. Lembre: a setinha => é o = seguido de >. Sua IDE (IntelliJ/VSCode) pode desenhar ⇒, mas você digita os dois caracteres separados.
eventos.jsJavaScript
const botao = document.querySelector("#curtir");
let contador = 0;

// "quando o botão receber um clique, rode esta função"
botao.addEventListener("click", () => {
  contador++;
  botao.textContent = `Curtidas: ${contador}`;
});

Esses dois aqui funcionam de verdade — clique no botão e digite no campo. Veja o console embaixo registrar cada evento 👇

Os eventos mais comuns: "click" (clique), "input" (digitar num campo), "submit" (enviar um formulário). É sempre o mesmo molde: elemento.addEventListener("evento", () => { ... }).

Crie contador.html e abra no navegador
Um HTML pequeno + um script no fim do body
contador.htmlHTML
<!DOCTYPE html>
<html lang="pt-BR">
<body>
  <h1 id="placar">Curtidas: 0</h1>
  <button id="curtir">Curtir ❤</button>

  <!-- o script vai no FIM: aí os elementos já existem -->
  <script>
    const placar = document.querySelector("#placar");
    const botao = document.querySelector("#curtir");
    let curtidas = 0;

    botao.addEventListener("click", () => {
      curtidas++;
      placar.textContent = `Curtidas: ${curtidas}`;
    });
  </script>
</body>
</html>

🍽️
Seu primeiro fetch — buscar dados da internet
Trazer pra sua página dados que moram em outro computador

Até agora, todo dado que apareceu nas suas páginas você digitou na mão — o título, o texto, os itens da lista. Mas e quando os dados são milhares e mudam toda hora (os produtos de uma loja, os posts de uma rede social, as mensagens de um chat)? Eles não cabem — nem ficam — dentro do seu arquivo. Eles moram em outro computador, ligado na internet o tempo todo.

🍽️ Imagine um restaurante

Você senta na mesa — essa mesa é o seu navegador. Você faz um pedido ao garçom; o pedido viaja até a cozinha (um computador lá longe), que prepara e te manda o prato de volta. Você não precisa saber cozinhar, nem entrar na cozinha — só pedir e receber.

Essa cozinha que atende pedidos pela internet tem um nome: API. E o computador onde ela roda é o servidor. Por enquanto a gente só vai sentar na mesa e pedir. 🍽️ (Lá na frente, no módulo de back-end, é você que vai construir uma cozinha dessas — a sua própria API.)

💡 Quatro palavras que todo dev fala o dia inteiro
  • Servidor 🌐 — um computador na internet que fica ligado esperando pedidos (a cozinha).
  • API 📖 — o "cardápio" desse servidor: a lista de coisas que você pode pedir a ele.
  • Requisição (request) ➡️ — o pedido que seu navegador manda. Resposta (response) ⬅️ — o que volta.
  • Endpoint 📍 — o endereço de UM pedido específico, como um item do cardápio (ex.: /produtos).

Para fazer esse pedido, o JavaScript tem uma palavra pronta: fetch (em inglês, "buscar"). Você dá a ela o endereço (a URL da API) e ela vai lá buscar pra você. Vamos pedir de uma API pública de verdade, que devolve uma lista de produtos:

produtos.jsJavaScript
// 1) faz o pedido a uma API pública (você pode abrir essa URL no navegador!)
fetch("https://fakestoreapi.com/products")
  // 2) quando a resposta chegar, transforma o JSON em lista de objetos JS
  .then((resposta) => resposta.json())
  // 3) agora sim: com os dados na mão, mexe no DOM
  .then((produtos) => {
    console.log(produtos); // uma lista de objetos
  });
⏳
O pedido demora (a comida não chega na hora). Por isso o .then(): ele quer dizer "quando a resposta voltar, ENTÃO faça…". Você não trava a página esperando — o JS avisa quando chegar. (Existe uma forma mais nova de escrever isso, o async/await; a gente vê com calma mais pra frente. Por enquanto, .then() já resolve.)

Mas em que formato o prato chega? Quase toda API do mundo responde no mesmo idioma: JSON. Boa notícia: ele é igualzinho aos objetos e arrays que você já viu no Cap 2 — uma lista [ ] de objetos { }, cada um com "campo": valor. Olha a anatomia dele com calma 👇

🕵️
Quer ver JSON de verdade agora? Abra https://fakestoreapi.com/products direto na barra do navegador. Aquele monte de { } e [ ] é exatamente o que o fetch vai te trazer. Cada API escolhe os nomes dos seus campos — nesta aqui eles são title (nome) e price (preço), e vêm em inglês porque é uma API de exemplo gringa. Tudo bem: o que importa é o formato.

Com a lista na mão, é o mesmo forEach do Cap 2: a gente percorre e cria um <li> para cada produto.

produtos.js (a parte que desenha)JavaScript
const lista = document.querySelector("#lista");

// nesta API os campos se chamam title e price (cada API tem os seus)
produtos.forEach((p) => {
  const item = document.createElement("li");
  item.textContent = `${p.title} — US$ ${p.price}`;
  lista.appendChild(item);
});

💡 Onde isso vai dar

Você acabou de aprender o lado cliente: pedir dados com fetch e jogar na tela. Nos próximos capítulos a gente faz exatamente isso dentro do React. E lá na frente, no módulo de back-end, você vai aprender o outro lado — vai construir a sua própria API (a sua cozinha!) e aí o fetch vai pedir os dados pra ela, não mais pra uma API gringa de exemplo. Quando os dois lados se encontram, você é fullstack. 🚀

🐛
BugZilla ataca o DOM!
Os tropeços clássicos de quem começa com a página
🐛
Bug 1 — o script rodou antes do elemento existir. Se o <script> vem antes do HTML, o querySelector não acha nada (vem null). Conserto: ponha o script no fim do body, ou use <script src="app.js" defer></script> no <head> — o defer segura o JS até a página carregar.
🐛
Bug 2 — "Cannot read properties of null". O terror do iniciante! Quase sempre é o seletor digitado errado: você escreveu querySelector("titulo") sem o #, ou errou o nome. Sem #/. ele procura uma tag chamada "titulo" — que não existe — e devolve null.
🐛
Bug 3 — esqueceu o .value do input. Para ler o que a pessoa digitou, é input.value (não o elemento direto). campo.value = o texto; campo sozinho = a caixinha inteira.
👀 Macete de ouro do BugZilla▼
🔦
Travou? Abra o Console (F12) e leia a mensagem vermelha — ela diz a linha e o que deu errado. Depois faça console.log(meuElemento): se aparecer null, o problema é o seletor; se aparecer o elemento, o problema é o que você fez depois. 90% dos bugs de DOM são uma dessas duas coisas.

Passo 5 — listar produtos de verdade (com o prof)
Array no formato da API + forEach
🎯 Tarefa

Em cima do arquivo, crie um array produtos no mesmo formato que uma API devolveria (objetos com id, nome, preco). Repare: como esse array é seu, você escolhe os nomes dos campos — aqui em português. Percorra com forEach e desenhe um <li> por produto.

app.js (no topo)JavaScript
// 👉 este array é temporário. Quando você aprender back-end, ele vira um fetch numa API de verdade!
const produtos = [
  { id: 1, nome: "Teclado Mecânico", preco: 320 },
  { id: 2, nome: "Monitor 27 polegadas", preco: 1450 },
  { id: 3, nome: "Cadeira Gamer", preco: 980 },
];

produtos.forEach((p) => {
  const item = document.createElement("li");
  item.textContent = `${p.nome} — R$ ${p.preco}`;
  lista.appendChild(item);
});
🔮
Guarde bem este array. Mais pra frente, quando você souber buscar dados, a gente vai apagar o const produtos = [...] e trocar por um fetch — três linhas, e a lista passa a vir de uma API de verdade, sem você digitar produto nenhum na mão.

O que você leva deste capítulo
A base que faz o React fazer sentido
  • DOM: o navegador transforma seu HTML numa árvore de objetos vivos. A porta é document.
  • Selecionar: querySelector("#id") (o primeiro) e querySelectorAll(".classe") (todos).
  • Mudar: .textContent, .style e .classList.
  • Eventos: elemento.addEventListener("click", () => { ... }).
  • API, requisição, resposta, JSON: pedir dados a um servidor na internet — e o fetch(url).then(...) que traz esses dados pra dentro da tela.
🎫 Quiz de saída: qual o conserto do erro Cannot read properties of null ao usar querySelector?
