Mas tem uma coisa que o JavaScript fez o tempo todo, sem você perceber: ele nunca disse "não". Fosse o que fosse que você mandasse, ele rodava. E rodar nem sempre é acertar. Olha três casos — digita e roda cada um no VSCode se quiser sentir na pele.

🩹 Dor 1 — a conta que "deu certo"

Uma idade que veio de um <input> (e input sempre entrega texto, lembra do Cap 3?). Você soma 1. Quanto dá?

dor1.jsJavaScript
let idade = "32";          // veio de um input: é TEXTO, com aspas
console.log(idade + 1);   // 32 + 1 = 33... né?

Rodou. E mentiu. O + viu um texto de um lado e colou o 1 na ponta: "32" + 1 = "321". Nenhum aviso, nenhum sublinhado vermelho, nenhum erro. Se isso fosse a idade de um cliente no seu sistema, ele teria 321 anos — e você só descobriria quando alguém reclamasse.

🩹 Dor 2 — o campo que ninguém cobrou

Um produto do GestorPRO, montado na mão. Você esqueceu o estoque. O JS avisa?

Não avisa. O objeto { } aceita qualquer combinação de campos — três, dois, nenhum. Pediu um que não existe? undefined, e segue o baile. No GestorPRO, o card desse produto fica assim:

🩹 Dor 3 — a cozinha que aceita banana como preço

Agora o pior. Alguém cadastra um produto pela sua tela do Cap 10, só que o preco chega como texto — "banana". O json-server, que é quem "guarda" os dados, faz o quê?

dor3.jsJavaScript
axios.post("http://localhost:3000/produtos", { nome: "Cabo HDMI", preco: "banana" })
  .then((resposta) => {
    console.log(resposta.status);              // o que o json-server respondeu
    console.log(resposta.data.preco * 2);   // a conta que o dashboard faria

201 é o código de "criado, tudo certo!". O json-server olhou pra "banana" no campo preço, achou lindo, e guardou. Aí o dashboard tenta fazer uma conta com esse preço e o resultado é NaN — Not a Number, "não é um número". Você já viu esse bicho no Cap 2. A diferença é que agora ele está salvo no seu banco, esperando pra quebrar o relatório de alguém.

💡 Spring é o React do backend

Guarda essa frase, porque ela custa zero e vale o sábado inteiro. O React não é uma linguagem: é um jeito organizado de usar JavaScript pra montar o salão (componentes, props, rotas). 👨‍🍳 O revisor lê a receita inteira antes de acender o fogão

Dois cozinheiros, a mesma receita.

O primeiro é o JavaScript. Ele acende o fogão e vai lendo a receita enquanto cozinha: passo 1, passo 2, passo 3… No passo 7 está escrito "2 xícaras de banana" onde devia ter um número. A panela já está quente, o óleo já está fervendo — ele improvisa, joga alguma coisa lá dentro e segue. O prato sai. Errado, mas sai. E vai pra mesa.

O segundo é o Java. Na cozinha dele existe um revisor. Antes de acender qualquer coisa, o revisor lê a receita inteira, do título ao último passo. Achou "2 xícaras de banana" onde devia ter número? Devolve a receita com um bilhete: "passo 7: isso não é um número". O fogão nem esquenta. Nenhum prato errado chega na mesa.

Esse revisor tem nome: compilador. Em Java, ele se chama javac.

É essa a diferença que muda o jogo. No JS, o caminho do seu código até a tela é curto — o Node lê e executa ao mesmo tempo (por isso dizem que o JS é interpretado). No Java o caminho tem uma estação a mais, e ela fica antes de tudo:

  • 📄 Main.java — a receita. Texto puro, o que você digita na IDE. O nome termina em .java, igual seus arquivos terminavam em .js.
  • 🧑‍⚖️ javac — o fiscal (o compilador). Lê o arquivo inteiro: confere se cada caixa recebeu o tipo que a etiqueta diz, se cada linha terminou com ;, se cada nome existe. Achou um erro? Devolve a lista, com número da linha — e não produz nada.
  • 📦 Main.class — o bytecode. A sua receita traduzida pra uma língua que só a JVM lê. Você nunca abre esse arquivo. Ele só nasce se o fiscal aprovou.
  • ☕ JVM — o fogão (Java Virtual Machine). É quem roda o Main.class. O mesmo fogão existe pra Windows, Mac e Linux — mais sobre isso já já.
  • 🖥️ console — o que aparece na tela. Igual ao de sempre.
🎁 Erro de compilação não é castigo

Quando o fiscal barra o seu código, a primeira sensação é de bronca: "não compilou, não rodou, não funciona". É o oposto. Aquilo é o bug sendo pego de graça — antes de rodar, com linha e coluna apontadas, sem nenhum cliente ver. No JS você pagava por esse mesmo bug com um NaN na tela de alguém. Em Java você paga com um sublinhado vermelho na sua IDE. É muito mais barato.

Bora ver na prática. O mesmo programinha, nas duas línguas — a idade certa, sem aspas:

main.jsJavaScript
let idade = 32;
console.log(idade + 1);
Main.javaJava
public class Main {
    public static void main(String[] args) {
        int idade = 32;                // a caixa idade, com etiqueta int
        System.out.println(idade + 1);   // o console.log do Java
    }
}
🙏 O ritual do main — aceite por 10 minutos

As duas primeiras linhas do Java (public class Main { e public static void main(String[] args) {) são o ritual de abertura: a porta que a JVM procura pra começar a rodar. Sim, é muita palavra pra dizer "comece aqui". Não decore nada agora — na próxima seção a gente abre essas palavras uma por uma. Por 10 minutos, aceite: o que importa está no meio. E System.out.println é o console.log de sobrenome comprido.

🧠 O que é a JVM (versão curta)

O fiscal não traduz o seu código direto pra Windows ou pra Mac. Ele traduz pra bytecode (o .class) — uma língua intermediária que só a JVM entende. E existe uma JVM pra cada sistema: Windows, Mac, Linux, o servidor da nuvem. O mesmo Main.class roda em todos. É daí que vem o lema do Java desde os anos 90: "write once, run anywhere" — escreva uma vez, rode em qualquer lugar. Quando o backend do GestorPRO for pro servidor, é isso que vai acontecer: o .class que compilou no seu notebook roda lá, sem mudar nada.

🍳 JDK, JRE e IDE: fogão, panelas e a cozinha montada

O JDK (Java Development Kit) é o kit completo: o fogão (a JVM, que roda o programa), as panelas (as bibliotecas — a String, o System.out, a ArrayList que vem daqui a pouco) e o fiscal (o javac, que compila). Existe também o JRE (Runtime Environment), que é só o fogão: serve pra quem vai rodar um programa pronto, não pra quem vai escrever. Você vai escrever — então é JDK.

E a IDE é a cozinha montada: bancada, gaveta com as panelas à mão, botão de ligar o fogão. No front era o VSCode. No backend é o IntelliJ IDEA. É ele que junta tudo: você escreve, aperta um botão e a IDE chama o fiscal e depois o fogão por você.

🔁 Por que trocar o VSCode pelo IntelliJ?

Não é implicância. Três motivos bem práticos:

  • É a IDE do backend. Todo o material de Spring do próximo sábado em diante é no IntelliJ — os menus, os atalhos, as telas. Aprender aqui hoje é adiantar aquilo.
  • Ele escreve Java por você. Construtores, getters, setters (você vai saber o que são daqui a pouco) — o IntelliJ gera com um atalho. No VSCode você ia digitar tudo na mão.
  • Roda com um ▶. Nada de terminal com javac e depois java: um clique no botão verde e ele compila, roda e mostra a saída embaixo.

O VSCode continua existindo pro seu React. A partir de hoje você tem duas cozinhas — uma pra cada lado do restaurante.

Tour de três linhas, porque é só isso que interessa hoje:

📂 src/

A pasta do seu código — a mesma ideia da src/ do React. Tudo que você escrever hoje mora aqui dentro.

☕ Main.java

O arquivo por onde o programa começa. O IntelliJ já encheu ele de exemplo e comentários — você vai limpar daqui a pouco.

▶ o botão verde

No topo à direita (e também na margem esquerda, ao lado da classe). É o "ligar o fogão": compila e roda.

Antes de rodar, olha o que o IntelliJ escreveu. No meio do arquivo tem uma linha que vai aparecer em todo programa Java que você fizer na vida — e ela assusta na primeira vez. Vamos ler peça por peça:

public static void main(String[] args) {
public = porta aberta: qualquer um pode chamar static = não precisa de ficha (explico daqui a pouco) void = não devolve nada, só faz main = o nome que a JVM procura pra começar String[] args = ritual: aceite hoje
🕯️ Ritual: decore por hoje, entenda na hora certa

Quando a JVM liga, ela procura dentro da classe um método chamado exatamente main, com exatamente essa cara. Achou? Começa por ali. Não achou? Nem liga. Por isso essa linha é sempre igual. Cada palavra dela volta com explicação própria ainda hoje: void na seção de métodos, static logo depois, public quando o cofre aparecer. O String[] args é a única que não volta — é uma lista de textos que o terminal pode passar pro programa, e a gente nunca vai usar. Copie sem culpa. Todo dev Java do mundo copiou essa linha antes de entender.

Dentro do main tem a outra linha que você vai digitar mil vezes: System.out.println(...). É o console.log com sobrenome: System é a classe do sistema, out é a saída dela (o console) e println é "imprime e pula linha" (print line). 🏷️ A caixa com etiqueta

No Cap 2 você aprendeu que variável é uma caixinha com nome: let idade = 25. Nome na caixa, valor dentro, pronto. Em Java a caixinha ganha uma segunda coisa: uma etiqueta de tipo colada na frente, dizendo o que pode entrar ali — "só texto", "só número inteiro", "só true ou false".

📋 A receita diz "2 ovos", não "2 alguma coisa"

Uma receita de bolo de verdade lista os ingredientes com tipo: 2 ovos, 200 g de farinha. E diz o que sai do forno: um bolo. Ninguém escreve "2 alguma coisa" e torce pra dar certo. Em Java, um método é isso: uma receita em que cada ingrediente tem etiqueta (os parâmetros) e o que sai também tem etiqueta (o retorno). Mandou farinha onde era ovo? O fiscal barra antes de acender o fogão.

🧭 Como ler um método (da esquerda pra direita)

Bate o olho em quatro coisas, sempre nessa ordem:

  • Tipo de retorno — a etiqueta do que sai pela rampa. int: esse método devolve um inteiro. Sempre.
  • Nome — dobro, em camelCase, igual às funções do JS.
  • Parâmetros tipados — (int n): cada ingrediente com a etiqueta na frente. Dois parâmetros? (double preco, int porcentagem), separados por vírgula.
  • return — o que sai. E aqui o fiscal confere: prometeu int? Então o return tem que entregar um int.

Não some com as chaves nem com o ; — em Java o return é sempre escrito na mão (não tem o "return automático" da arrow sem chaves).

E quando o método não devolve nada — só faz alguma coisa, tipo imprimir? A etiqueta do retorno é void ("vazio"). Um método void não tem return com valor: ele executa e pronto. Você já viu um: o main é void.

Chamar é igual ao JS — e o resultado vai pra uma caixa com a etiqueta certa:

dentro do mainJava
int r = dobro(5);          // r recebe 10 — e r PRECISA ser int, porque dobro devolve int
System.out.println(r);   // 10

☎️ E esse static?

Pensa numa empresa. O telefone da empresa é um só: pertence à empresa, não a ninguém em particular — qualquer pessoa liga pra ele sem precisar saber quem está na mesa. Isso é static: o método pertence à classe (Main), e você chama direto. Já o celular de cada funcionário é diferente: cada ficha de funcionário tem o seu número. Isso é um método sem static: ele pertence a uma ficha, a um objeto.

No Main tudo é static por enquanto — o main é static, então tudo que ele chama direto também precisa ser. Quando a gente tiver fichas (objetos, na próxima seção), os métodos vão morar nelas, sem static. Volto nisso na seção do Service — prometo.

Em Java não existe { } solto — precisa do molde

Lembra da Dor 2? Vamos revisitar ela no lugar onde ela mora: a lista de produtos do GestorPRO. No JS, cada produto era um { } solto — e nada, nada, obrigava os quatro a terem os mesmos campos. Um jeito bem comum de isso dar errado:

Quatro objetos, quatro "formatos" possíveis. O JS não tem como saber que um produto precisa ter estoque — porque você nunca disse isso a ele. Cada { } é uma folha em branco onde você escreve o que quiser. Ou esquece o que quiser.

Em Java isso não existe. Não tem { } solto. Antes de criar um produto que seja, você descreve o molde: quais campos um Produto tem e de que tipo é cada um. Só depois o Java te deixa criar produtos — e todos saem com o mesmo formato, sempre.

🗂️ A ficha de cadastro

Pensa naquela ficha de cadastro de papelaria: os campos já vêm impressos — NOME, PREÇO, ESTOQUE — e embaixo de cada um, uma linha em branco esperando caneta.

A classe é a ficha em branco. Ela define quais campos existem (e o tipo de cada um), mas não tem nenhum produto dentro. É só o desenho.

O objeto é uma ficha preenchida: Teclado Mecânico, 320, 12. Cada produto é uma ficha diferente, com os mesmos campos e valores próprios.

E o new é o gesto de pegar uma ficha em branco da pilha. Pega uma, preenche. Pega outra, preenche. A pilha nunca acaba.

Guarda essa imagem com carinho: no backend, quando você vir @Entity em cima de uma classe, é a mesma ficha — só que com uma etiqueta dizendo "esta ficha vira tabela no banco".

A ficha vira um arquivo novo. No IntelliJ: botão direito no pacote br.com.sistemagestao.api → New → Java Class → digite Produto → Enter. O IntelliJ cria o Produto.java já com o package na primeira linha e a classe vazia. Preencha assim:

  • String nome; — um campo. É a variável com etiqueta de tipo que você viu na seção de tipos… só que sem valor. A ficha está em branco.

  • Repara no que não tem: static, main, println. A ficha não roda nada. Ela só descreve.
📁 Um arquivo por classe

Em Java, o nome do arquivo tem que ser igual ao nome da classe pública: Produto.java guarda public class Produto. Renomeou um e não o outro? O fiscal barra: error: class Produto is public, should be declared in a file named Produto.java. Por isso, crie classe sempre pela IDE (New → Java Class): ela acerta o nome dos dois de uma vez.

E a convenção de nomes, que todo código Java do planeta segue: classe em PascalCase (Produto, ProdutoService, Main); campo e método em camelCase (nome, estoque, estoqueBaixo). O Java não te obriga — mas o Spring conta com isso pra achar seus campos. Siga.

Na seção de métodos você escreveu receitas static dentro do Main, e tudo o que a receita precisava chegava por parâmetro. Agora imagina uma receitinha grampeada em cada ficha: "estoque baixo? olha o MEU estoque e responde".

🏨 A recepção não entrega ficha sem os campos obrigatórios

Pensa no check-in de um hotel. Você não recebe a chave do quarto e "depois preenche o que der". A recepcionista segura a ficha e pergunta: nome? documento? data de saída? Enquanto faltar um campo obrigatório, a chave não sai do balcão. Os campos opcionais (o número de fidelidade, por exemplo) ficam em branco — sem problema.

O construtor é essa recepcionista. Até agora, new Produto() te entregava a ficha vazia e confiava que você ia preencher. A partir de hoje, pra sair uma ficha do new, você entrega os campos obrigatórios na porta: new Produto("Mouse Gamer", 89, 2). Esqueceu o estoque? A ficha nem nasce — o javac barra ali, antes de rodar.

🏗️ O que é um construtor

É um método especial que roda uma vez, na hora do new. Ele recebe os dados pela porta (parâmetros com tipo, igual aos métodos da seção ⚙️) e guarda cada um na gaveta certa da ficha. Você não chama ele pelo nome — o new chama por você. Vamos ver o Produto inteiro, e depois eu desmonto peça por peça.

Abra o Produto.java e deixe ele assim. Tem 4 novidades em relação à seção passada (um campo novo, dois construtores e um método com um @ em cima) — cada uma explicada logo abaixo. Pode digitar à mão ou deixar o IntelliJ gerar os construtores (mostro como daqui a pouco):

src/br/com/sistemagestao/api/Produto.java — v2 (o arquivo inteiro)Java
package br.com.sistemagestao.api;

public class Produto {
    Long id;            // NOVO: nasce null — quem dá o número é o Service
    String nome;
    double preco;
    int estoque;

    public Produto() {      // construtor VAZIO: a ficha em branco de antes
    }

    public Produto(String nome, double preco, int estoque) {   // construtor CHEIO
        this.nome = nome;
        this.preco = preco;
        this.estoque = estoque;
    }

    boolean estoqueBaixo() {       // igual à seção passada
        return estoque < 5;
    }

    @Override
    public String toString() {
        return "#" + id + " " + nome + " - R$ " + preco + " (estoque: " + estoque + ")";
    }
}
🔢 Novidade 1 — Long id: o número que ninguém preenche na porta

Lembra do "id": 1 no db.json? Era o json-server quem inventava esse número — você nunca mandou id no axios.post. Aqui é igual: o id é um campo da ficha, mas não entra no construtor. Ele nasce null (por isso é Long com maiúscula, a caixa que aceita vazio — seção 🔤) e quem dá o número é o ProdutoService, daqui a duas seções. No backend, quem dá é o banco de dados 🐘. A recepção não pergunta o número do quarto: isso é o hotel quem decide.

Novidade 2 — o construtor cheio. Leia a primeira linha dele com calma, porque ela parece um método… mas tem uma coisa faltando de propósito:

public Produto(String nome, double preco, int estoque) {
public = porta aberta: qualquer classe pode chamar Produto = o nome do construtor É o nome da classe (obrigatório) parâmetros com tipo = o que a recepção exige na porta SEM tipo de retorno: nem void, nem String — nada antes do nome

Compara com um método normal: boolean estoqueBaixo() tem o tipo de retorno antes do nome. O construtor não tem nada antes do nome — nem void. É assim que o Java sabe que aquilo é um construtor e não um método: mesmo nome da classe, sem tipo na frente. Se você escrever public void Produto(...) por reflexo, o Java aceita como um método comum chamado Produto — que nunca vai rodar no new. Sem tipo, sem return.

🫵 E esse this?

📌 Anotação é um post-it que alguém lê

O @Override é a sua primeira anotação. Anotação não é código que roda: é uma informação colada em cima de uma classe, de um campo ou de um método — um post-it. Quem lê o post-it faz alguma coisa com ele. O @Override diz: "estou reescrevendo um método que já existia". Quem lê é o javac: ele confere se existe mesmo um método com esse nome pra reescrever. Se você digitar tostring (t minúsculo) por engano, sem o post-it o Java criaria um método novo e inútil, e o println continuaria imprimindo Produto@15db9742 — em silêncio. Com o post-it, o javac barra na hora: "não existe tostring pra você sobrescrever".

A metáfora termina aqui: não existe um banco de verdade. Tecnicamente, estamos controlando o acesso ao estado do objeto. Isso se chama encapsulamento.

package br.com.sistemagestao.api;

import java.util.ArrayList;
import java.util.List;

public class ProdutoService {
    private List<Produto> produtos = new ArrayList<>();
    private Long proximoId = 1L;

    public void cadastrar(Produto produto) {
        produto.setId(proximoId);
        proximoId++;
        produtos.add(produto);
    }

    public List<Produto> listar() {
        return produtos;
    }

    public List<Produto> estoqueBaixo() {
        List<Produto> baixos = new ArrayList<>();
        for (Produto p : produtos) {
            if (p.estoqueBaixo()) { baixos.add(p); }
        }
        return baixos;
    }

    public Produto buscarPorId(Long id) {
        for (Produto p : produtos) {
            if (p.getId().equals(id)) { return p; }
        }
        return null;
    }

    public void remover(Long id) {
        Produto achado = buscarPorId(id);
        if (achado != null) { produtos.remove(achado); }
    }
}

Leia por responsabilidade: cadastrar carimba o id e guarda; listar devolve a lista; estoqueBaixo filtra sem streams; buscarPorId percorre e pode devolver null; remover reaproveita a busca.

1 · ';' expected

Quase sempre faltou ; no fim da linha anterior. O ^ aponta onde o compilador desistiu, não necessariamente onde o erro começou.

2 · Maiúscula importa

system.out → package system does not exist. string nome → cannot find symbol: class string. São System e String.

3 · O L do Long

class Produto is public, should be declared in a file named Produto.java. Classe pública Produto mora em Produto.java; crie pela IDE.

7 · == em String

== compara se é o mesmo objeto; .equals() compara o conteúdo. Use nome1.equals(nome2). Dois literais podem enganar e parecer funcionar por causa do pool de Strings.

Se buscarPorId percorreu a lista e não encontrou, ainda precisa devolver algo. Depois do for, escreva return null;.
