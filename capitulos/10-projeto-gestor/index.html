🍽️ O salão e a cozinha: por que DOIS servidores

Aqui vem a parte que mais confunde, então vamos com calma — e é a mesma cozinha de treino que você subiu no Cap 7, agora com três coleções em vez de uma. A partir de agora o seu computador vai rodar dois programas ao mesmo tempo, e cada um tem um trabalho: o Vite (aquele do npm run dev) é o salão do restaurante — ele monta e serve a TELA que o usuário vê. O json-server é a cozinha — ele guarda e devolve os DADOS, e ninguém do salão entra lá: pra pedir qualquer coisa, o garçom (axios) leva o pedido até a portinhola. Salão sem cozinha: a tela abre, mas as tabelas vêm vazias e com erro. Cozinha sem salão: os dados existem, mas não tem tela nenhuma. Você precisa dos dois de pé, ao mesmo tempo, o tempo todo.

Repare que o terminal não devolve o $ depois desse comando: ele fica "preso", mostrando o Vite vivo. Isso é o certo — servidor é um programa que não termina, fica esperando visita. Muito aluno acha que travou e aperta Ctrl+C, que é justamente o comando pra MATAR o servidor. Deixe quietinho e abra outro terminal.
🤔 npx? Mas eu não usei sempre "npm install"?

Boa pergunta — e a diferença é de gente grande. O npm install axios baixa e GUARDA o programa dentro do seu projeto (na node_modules, anotado no package.json): é assim com o que faz parte do site. Já o npx json-server significa "baixa, usa agora e não guarda" — perfeito para uma ferramenta que só serve enquanto você desenvolve e que não vai junto quando o site for publicado. O json-server é exatamente isso: um faz-de-conta de backend, um andaime. Quando a API de verdade (a sua, em Java!) existir, o andaime é retirado e nada no seu React precisa mudar de lugar.

Os 3 perrengues clássicos dos dois terminais (todos vão acontecer com alguém da turma hoje — quando acontecer com você, volte aqui):
  • "Fechei o terminal e o site quebrou" — a tela mostra 😵 Não consegui falar com o servidor e o console grita Network Error (o mesmo Bug 5 do Cap 7 — é o jeito do axios dizer "bati na porta e não tinha ninguém").   • "Port 3000 is already in use" (ou EADDRINUSE) — já tem um json-server rodando, provavelmente esquecido em outro terminal ou de outra aula. Ache o terminal antigo e dê Ctrl+C nele; depois suba de novo. (Dá pra usar outra porta com --port 3001, mas aí TODAS as URLs do seu código mudam — não vale a pena hoje.)
  • "Ele criou um db.json vazio / não achou minhas coleções" — você rodou na pasta errada. O comando tem que ser dado na raiz do gestorpro. Confira com ls (ou dir no Windows): você precisa ver db.json e package.json na lista.

Os 4 verbos do HTTP (a teoria nova do capítulo)
Até hoje você só PEDIA dados. Hoje aprende a criar, trocar e apagar

Hora da única teoria realmente nova do projeto — e ela é deliciosa de simples. Desde o Cap 7, toda conversa sua com a API foi axios.get(...): GET é o verbo de pedir para ler. Mas o HTTP tem outros verbos, e um sistema de gestão usa os 4 principais:

🏤 O balcão do cartório

Pensa no json-server como um cartório com um arquivo de fichas (o db.json). Você chega no balcão e o VERBO do seu envelope diz o que quer fazer: GET = "me mostra as fichas" (só leitura, nada muda) · POST = "registra esta ficha NOVA" (o cartório carimba um id novo) · PUT = "TROCA a ficha de número X por esta aqui" (por isso a URL leva o id!) · DELETE = "rasga a ficha de número X". Mesmo balcão, mesmo endereço — o verbo muda tudo.

No axios, cada verbo é um método com a mesma cara do get que você já usa:

a família completa do axiosJS
// LER a lista (o velho conhecido do Cap 7):
axios.get("http://localhost:3000/clientes")

// CRIAR: o 2º argumento é o objeto com os dados da ficha nova
// (repare: SEM id — quem carimba o id é o servidor!)
axios.post("http://localhost:3000/clientes", { nome: "Diego", cidade: "Patos" })

// TROCAR: o id vai na URL (QUAL ficha) e o objeto novo vai no 2º argumento
axios.put("http://localhost:3000/clientes/2", { nome: "Bruno Lima", cidade: "Sousa" })

// APAGAR: só a URL com o id — não tem "corpo", só o alvo
axios.delete("http://localhost:3000/clientes/3")
📛 O nome de mercado: CRUD

Esse quarteto tem apelido famoso: CRUD — Create (POST), Read (GET), Update (PUT), Delete (DELETE). Quando uma vaga pedir "experiência com CRUD", é ISSO: cadastrar, listar, editar e excluir. Ao fim de hoje, você terá feito um CRUD triplo — pode escrever no currículo sem corar. 😄

🌍 O conceito-mor do CRUD: dois mundos

Olha o .then() com carinho, porque ele carrega A lição do capítulo: o axios.delete apaga a ficha no servidor — mas a tela mostra o estado, que é outro mundo (é a cópia que o useEffect trouxe lá no início). Se você não atualizar o estado, o cliente excluído continua na tela até o próximo F5 — o sistema fica parecendo quebrado sem estar. Por isso o setClientes(clientes.filter(...)): o .filter (Cap 2/6!) monta uma lista nova sem o excluído — repare no !==, "ficam só os que NÃO têm esse id" — e o set redesenha. Servidor atualizado + estado atualizado = os dois mundos em paz.

🎯
E o onClick={() => excluir(c.id)}? É a arrow inline do Cap 6 — precisamos passar o id do cliente DAQUELA linha, então embrulhamos a chamada numa função. Sem o embrulho (onClick={excluir(c.id)}) ela executaria na renderização — a pegadinha clássica.

import { useState, useEffect } from "react"
import { Link } from "react-router-dom"
import axios from "axios"
import styles from "./Dashboard.module.css"

const Dashboard = () => {
  const [clientes, setClientes] = useState([])
  const [fornecedores, setFornecedores] = useState([])
  const [produtos, setProdutos] = useState([])

  useEffect(() => {
    axios.get("http://localhost:3000/clientes").then((res) => setClientes(res.data))
    axios.get("http://localhost:3000/fornecedores").then((res) => setFornecedores(res.data))
    axios.get("http://localhost:3000/produtos").then((res) => setProdutos(res.data))
  }, [])

  const estoqueBaixo = produtos.filter((p) => p.estoque < 5).length

  return (
    <div className={styles.painel}>
      <h2>📊 Visão geral</h2>
      <div className={styles.cards}>
        <Link to="/clientes" className={styles.card}>
          <strong>{clientes.length}</strong> 👥 clientes
        </Link>
        <Link to="/fornecedores" className={styles.card}>
          <strong>{fornecedores.length}</strong> 🚚 fornecedores
        </Link>
        <Link to="/produtos" className={styles.card}>
          <strong>{produtos.length}</strong> 📦 produtos
        </Link>
      </div>
      {estoqueBaixo > 0 && (
        <p className={styles.alerta}>⚠️ {estoqueBaixo} produtos com estoque baixo</p>
      )}
    </div>
  )
}

export default Dashboard

Login & Registro (de mentira) fase 3
O fluxo de autenticação completo — com um crachá de brinquedo, por enquanto

Todo sistema de gestão tem uma porta na frente: login. A autenticação DE VERDADE (senha criptografada, token, validações) mora no servidor — e é uma das estrelas da metade backend do curso, em Java. Mas as TELAS e o FLUXO são trabalho de front, e dá pra construir tudo hoje com um truque honesto: uma coleção usuarios no json-server fazendo papel de "cadastro de funcionários".

🎫 Ferramenta nova: o localStorage

Quando você entra num sistema, o navegador precisa lembrar que você entrou — mesmo depois de um F5. O lugar disso é o localStorage: um bolsinho do navegador que guarda textos por site. Três movimentos: localStorage.setItem("chave", texto) guarda, localStorage.getItem("chave") lê, e localStorage.removeItem("chave") apaga. Como ele só guarda TEXTO, objetos entram com JSON.stringify(obj) e saem com JSON.parse(texto) — os mesmos tradutores de JSON que você conhece desde o Cap 3.

🚨
Combinado de gente honesta: aqui a senha vai ficar em texto puro no db.json — e isso é INACEITÁVEL num sistema real (qualquer um que abrir o arquivo lê a senha de todo mundo). Estamos fazendo assim porque o objetivo de hoje é o FLUXO das telas. Quando o backend Java chegar, o login vira uma chamada de verdade que devolve um token (o crachá oficial, assinado pelo servidor) e a senha vira um código embaralhado irreversível. As telas que você vai criar agora ficam — só troca a cozinha.
