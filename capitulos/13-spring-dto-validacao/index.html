01

DTO: o formulário da recepção

Por que a API não deveria receber a entidade inteira.

🏥 A recepção da clínica

Na clínica, você não entra na sala de arquivos para escrever no seu prontuário. Você preenche o formulário da recepção: nome, telefone, convênio. Não existe campo para “número do prontuário”: quem decide é a clínica. Lá dentro, uma pessoa copia os dados do formulário para o prontuário. Na saída, você recebe um comprovante, com coisas que você nunca escreveu: o número do atendimento, a data e a hora.

Onde a analogia para: o formulário não é uma tranca de segurança. Ele só define quais campos existem. Se algo não tem campo no formulário, não entra. Mas o que tem campo ainda pode vir errado; para isso existe a validação, no Encontro B.

O nome técnico

DTO significa Data Transfer Object, ou objeto de transferência de dados. É uma classe que só carrega os dados que atravessam a fronteira HTTP, em uma direção. Não tem regra de negócio e não vai para o banco. Na clínica, o formulário e o comprovante são DTOs; o prontuário é a entidade.

JSON que chega→ProdutoRequestDTOo formulário→Servicecopia os campos→Produtoa entidade→🐘 banco
JSON que sai←ProdutoResponseDTOo comprovante←Service←Produto←🐘 banco

São dois DTOs, um para cada direção. O de entrada diz o que o cliente da API pode mandar. O de saída diz o que a API mostra. A entidade continua existindo, mas agora fica do lado de dentro, conversando só com o banco.

Nosso Produto terá estes campos (os mesmos do GestorPRO que você construiu no React, mais um campo novo, criadoEm, a data e hora do cadastro):

02

record: um DTO em poucas linhas

Uma classe que só carrega dados, escrita pelo próprio Java.

No Cap 11 você escreveu classes com campos privados, construtor e getters. Um DTO só precisa disso: guardar dados e deixar ler. Veja como ficaria um DTO com apenas dois campos, escrito do jeito que você já conhece:

Antes · uma classe só para carregar dados (não digite)Java
public class ProdutoRequestDTO {
    private final String nome;
    private final BigDecimal preco;

    public ProdutoRequestDTO(String nome, BigDecimal preco) {
        this.nome = nome;
        this.preco = preco;
    }

    public String getNome() {
        return nome;
    }

    public BigDecimal getPreco() {
        return preco;
    }
}

Dezessete linhas para dois campos. Com quatro campos, seriam mais de trinta, todas previsíveis. O Java 16 trouxe uma forma curta para esse caso exato: o record.

Depois · o mesmo DTO, como record (não digite ainda)Java
public record ProdutoRequestDTO(String nome, BigDecimal preco) {
}

Leia assim: “um registro de dados com nome e preco”. Entre parênteses ficam os componentes do record. A partir deles, o Java gera sozinho os campos privados e final, o construtor com os dois valores, os métodos de leitura e alguns métodos auxiliares que você ainda não precisa.

Três diferenças que pegam iniciantes

1 · Ler sem “get”

O método de leitura tem o mesmo nome do componente: dto.nome(), e não dto.getNome().

2 · Sem setter

O record nasce pronto e não muda. Não existe setNome. Para um formulário recebido, é exatamente o que queremos.

3 · Só para DTO

A entidade continua com Lombok: o JPA precisa de construtor vazio e de alterar campos. Record é ótimo para DTO e ruim para entidade.

Os campos são final, como no Service do Cap 12: recebem valor uma vez, no construtor. Isso combina com a ideia de formulário: depois de entregue, ninguém rabisca.

04

Dinheiro não é double

Um experimento de 10 segundos que você já sabe fazer.

Abra o console do navegador com F12 (aba Console), como no Cap 2, e digite:

Console do navegadorJavaScript
0.1 + 0.2
O que apareceTexto
0.30000000000000004

Não é um bug do JavaScript. No Java acontece exatamente o mesmo: System.out.println(0.1 + 0.2); num main do Cap 11 imprime 0.30000000000000004. O computador guarda números com vírgula em binário, e alguns decimais simples não têm representação exata em binário, assim como 1/3 não tem em decimal (0,3333…). O double guarda uma aproximação muito boa, mas aproximação.

Para medir temperatura, isso não importa. Para dinheiro, importa: somando milhares de vendas, centavos aparecem ou somem, e o relatório não bate com o caixa.

BigDecimal: decimal exato

O Java tem uma classe para isso: BigDecimal, do pacote java.math. Ela guarda o número em decimal, do jeito que escrevemos. Um teste rápido, se quiser rodar num main do Cap 11:

Comparação · double × BigDecimalJava
System.out.println(0.1 + 0.2);
System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2")));
System.out.println(new BigDecimal(0.1));
Saída realTexto
0.30000000000000004
0.3
0.1000000000000000055511151231257827021181583404541015625

Repare na terceira linha. Criar um BigDecimal a partir de 0.1 (um double) copia a aproximação inteira. Quando criar à mão, use texto: new BigDecimal("0.1"). Na nossa API isso quase não aparece: o Spring converte o número do JSON direto para BigDecimal, sem passar por double.

No JSON, nada muda: o preço continua sendo um número, "preco": 320.00. No banco, vamos pedir uma coluna decimal com tamanho definido:

@Column(precision = 10, scale = 2)
AtributoSignificaNo nosso caso
precision = 10Quantos dígitos no total.Até 10 dígitos.
scale = 2Quantos desses ficam depois da vírgula.Sempre 2 casas: centavos.

Resultado: o maior preço possível é 99.999.999,99. No PostgreSQL, a coluna aparece como numeric(10,2).

No pacote model, crie a classe Produto. A estrutura é a mesma do Fornecedor; os tipos são novos:

import lombok.AllArgsConstructor;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;

import java.math.BigDecimal;
import java.time.LocalDateTime;

@Getter
@NoArgsConstructor
@AllArgsConstructor
@Table(name = "produtos")
@Entity
public class Produto {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "nome", nullable = false)
    private String nome;

    @Column(name = "preco", nullable = false, precision = 10, scale = 2)
    private BigDecimal preco;

    @Column(name = "estoque", nullable = false)
    private Integer estoque;

    @Column(name = "categoria")

    @Column(name = "criado_em", nullable = false)

TrechoPor quê

Passo 4 · Service: cadastrar

Alguém precisa copiar os dados do formulário para a entidade e, depois de salvar, montar o comprovante. Quem faz isso é o Service: ele é a camada que conhece os dois lados, o DTO e a entidade.

service/ProdutoService.javaJava
package com.gestorpro.api.service;

import com.gestorpro.api.dto.ProdutoRequestDTO;
import com.gestorpro.api.dto.ProdutoResponseDTO;
import com.gestorpro.api.model.Produto;
import com.gestorpro.api.repository.ProdutoRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

import java.time.LocalDateTime;

@Service
@RequiredArgsConstructor
public class ProdutoService {

    private final ProdutoRepository produtoRepository;

    public ProdutoResponseDTO cadastrar(ProdutoRequestDTO dto) {
        Produto produto = new Produto();
        produto.setNome(dto.nome());
        produto.setPreco(dto.preco());
        produto.setEstoque(dto.estoque());
        produto.setCategoria(dto.categoria());
        produto.setCriadoEm(LocalDateTime.now());

        Produto salvo = produtoRepository.save(produto);
        return new ProdutoResponseDTO(
                salvo.getId(),
                salvo.getNome(),
                salvo.getPreco(),
                salvo.getEstoque(),
                salvo.getCategoria(),
                salvo.getCriadoEm()
        );
    }
}

O método cadastrar faz quatro tarefas, nesta ordem:

  • Montar a entidade: new Produto() cria um produto vazio, e os quatro set copiam os campos do formulário. Repare no que não vem do formulário: id e criadoEm. Não existe de onde copiar.
  • Carimbar a data com o relógio do servidor (LocalDateTime.now()). A data é uma regra do servidor, por isso mora no Service.
  • Salvar: o save devolve a entidade já com o ID gerado pelo banco. Guardamos em salvo.
  • Montar o comprovante: new ProdutoResponseDTO(...) recebe os valores na mesma ordem dos componentes do record.
Duas formas de ler um valor. No formulário, que é um record, a leitura é dto.nome(), sem get. Na entidade, que tem @Getter do Lombok, é salvo.getNome(). Trocar uma pela outra é o erro de compilação mais comum desta seção.

R · Listar: a esteira

Converter uma lista inteira, e a primeira lambda do backend.

GEThttp://localhost:8080/produtos200 OK

O produtoRepository.findAll() devolve uma List<Produto>: entidades. Mas o Controller só fala DTO. Precisamos transformar cada Produto em um ProdutoResponseDTO e juntar tudo numa lista nova.

O cadastrar já sabe montar um comprovante: é o new ProdutoResponseDTO(...) do return. O listar vai precisar da mesma montagem, uma vez para cada produto. Em vez de copiar aquelas linhas, elas ganham um nome: o método paraResposta. Ele recebe uma entidade e devolve o comprovante. É private porque só o próprio Service usa.

O método novo, no fim do Service (não digite ainda)Java
private ProdutoResponseDTO paraResposta(Produto produto) {
    return new ProdutoResponseDTO(
            produto.getId(),
            produto.getNome(),
            produto.getPreco(),
            produto.getEstoque(),
            produto.getCategoria(),
            produto.getCriadoEm()
    );
}

Com ele, o listar precisa chamar paraResposta para cada produto da lista. Primeiro, do jeito que você já sabe, com for:

Versão com for · só para comparar (não digite)Java
public List<ProdutoResponseDTO> listar() {
    List<Produto> produtos = produtoRepository.findAll();
    List<ProdutoResponseDTO> respostas = new ArrayList<>();
    for (Produto produto : produtos) {
        respostas.add(paraResposta(produto));
    }
    return respostas;
}

Em Java, a mesma ideia fica assim:

🏭 A esteira

stream() liga a esteira e coloca os produtos nela, um atrás do outro. map(...) é uma estação de trabalho: cada produto que passa entra como entidade e sai como comprovante. toList() é a caixa no fim da esteira, que junta tudo numa lista nova. A lista original não muda.

Como ler produto -> paraResposta(produto)

Isso é uma lambda: uma função curta, sem nome, escrita no lugar onde é usada. É a mesma ideia da arrow function do Cap 2. À esquerda da seta, o parâmetro: o item que está passando (chamamos de produto, mas o nome é escolha sua). À direita, o corpo: o que fazer com ele. O resultado do corpo é devolvido automaticamente, sem return.

Javaproduto -> ...hífen + maior
⚠️ A seta do Java são dois caracteres: - seguido de >. O IntelliJ e o VS Code costumam desenhar os dois juntos como uma seta só (→), por causa de uma fonte com “ligaduras”. É só desenho: digite hífen e sinal de maior. Se você copiar uma seta → de algum lugar, o Java responde illegal character: '\u2192'. E se escrever a seta do JavaScript (=>), responde illegal start of expression.

  • orElseThrow quer dizer “me dê o que está na caixa; ou então, se estiver vazia, lance este erro”. Caixa cheia: a variável produto recebe o produto. Caixa vazia: o erro é lançado.

🎫 O segurança do show

Na porta do show, o segurança tem uma prancheta com regras: ingresso na mão, pulseira certa, maior de idade. Ele confere antes de deixar entrar. Quem é barrado não chega ao balcão do bar nem ao palco. E ele não precisa ligar para ninguém para conferir essas regras: está tudo na prancheta e no que a pessoa trouxe.

Na nossa API, a prancheta são anotações nos componentes do DTO, e o segurança é o próprio Spring, que confere o formulário antes de chamar o Controller. Isso se chama Bean Validation, a validação padrão do Java para objetos.

    A recepção explica o “não”
    Um tratador de erros para toda a API.
    

    Lembre do formulário do GestorPRO no Cap 10: quando algo estava errado, a tela mostrava uma mensagem perto do campo. Para isso, quem chama a API precisa saber qual campo falhou e por quê. Queremos uma resposta 400 assim:
    

    O 400 que queremosJSON
    {
  "nome": "O nome é obrigatório",
  "preco": "O preço deve ser maior que zero"
}
    

    Quando a validação falha, o Spring lança uma exceção chamada MethodArgumentNotValidException, carregando a lista de campos recusados e suas mensagens. Hoje ninguém trata essa exceção, e o Spring responde com o 400 genérico. Vamos criar uma classe que a trata.
    

    Uma recepção para todos os Controllers
    

    • @RestControllerAdvice marca uma classe que atende todos os Controllers quando algo dá errado. Uma classe só, e Produto, Fornecedor e Cliente passam a usá-la.
    • @ExceptionHandler(MethodArgumentNotValidException.class) diz: “quando essa exceção acontecer, chame este método”.
    • @ResponseStatus(HttpStatus.BAD_REQUEST): a resposta continua sendo 400, como no @ResponseStatus dos Controllers.
    • O retorno é um Map<String, String>: um dicionário de pares chave → valor, como um objeto do JavaScript. A chave é o nome do campo; o valor, a mensagem. O Spring o transforma no JSON acima.
    

    Crie o pacote exception e a classe TratadorDeErros:
    

    exception/TratadorDeErros.javaJava
    package com.gestorpro.api.exception;

import org.springframework.http.HttpStatus;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice
public class TratadorDeErros {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Map<String, String> tratarValidacao(MethodArgumentNotValidException erro) {
        Map<String, String> erros = new HashMap<>();
        for (FieldError campo : erro.getBindingResult().getFieldErrors()) {
            erros.put(campo.getField(), campo.getDefaultMessage());
        }
        return erros;
    }
}
    

    O for percorre cada campo recusado (FieldError) e coloca no dicionário o nome do campo (getField()) e a mensagem que escrevemos no DTO (getDefaultMessage()).

    O primeiro relacionamento: @ManyToOne.
    

    O Teclado Mecânico acabou. Para repor, precisamos saber de quem compramos. Essa informação já existe: a TechDistrib está na tabela de fornecedores desde o Cap 12. O que falta é ligar as duas fichas.
    

    🗂️ Ficha que aponta para ficha
    Imagine as fichas de papel do estoque. Na ficha do teclado, em vez de copiar o CNPJ, o telefone e o endereço da TechDistrib, alguém escreve só: “fornecedor nº 1”.     Onde a analogia para: no papel, ninguém impede de escrever “fornecedor nº 99”, que não existe. No banco, existe quem impeça.
    

    No banco: a chave estrangeira
    

    A tabela produtos ganha uma coluna fornecedor_id, que guarda o ID de uma linha da tabela fornecedores. Uma coluna que guarda a chave primária de outra tabela se chama chave estrangeira (em inglês, foreign key, ou FK). O PostgreSQL passa a garantir duas coisas: o número precisa existir na outra tabela, e não dá para apagar um fornecedor que ainda tem produtos apontando para ele.
    

    produtos1 · Teclado · fornecedor_id 12 · Mouse · fornecedor_id 13 · Monitor · fornecedor_id 1
    →
    fornecedores1 · TechDistrib2 · Papelaria Nordeste
    

    O relacionamento é lido a partir do Produto: muitos produtos para um fornecedor. Em inglês, many to one. Neste capítulo, só o Produto conhece seu fornecedor; o Fornecedor não ganha uma lista de produtos.

    Passo 4 · Service: dois repositories
    

    Para ligar o produto, o Service precisa perguntar ao FornecedorRepository se o fornecedor existe. Ele ganha uma segunda dependência, com o mesmo padrão private final do Cap 12, e um método gêmeo do buscarOuFalhar:
    

    service/ProdutoService.javaJava
    package com.gestorpro.api.service;

import com.gestorpro.api.dto.ProdutoRequestDTO;
import com.gestorpro.api.dto.ProdutoResponseDTO;
import com.gestorpro.api.model.Fornecedor;
import com.gestorpro.api.model.Produto;
import com.gestorpro.api.repository.FornecedorRepository;
import com.gestorpro.api.repository.ProdutoRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.web.server.ResponseStatusException;

import java.time.LocalDateTime;
import java.util.List;

@Service
@RequiredArgsConstructor
public class ProdutoService {

    private final ProdutoRepository produtoRepository;
    private final FornecedorRepository fornecedorRepository;

    public ProdutoResponseDTO cadastrar(ProdutoRequestDTO dto) {
        Produto produto = new Produto();
        produto.setNome(dto.nome());
        produto.setPreco(dto.preco());
        produto.setEstoque(dto.estoque());
        produto.setCategoria(dto.categoria());
        produto.setFornecedor(buscarFornecedorOuFalhar(dto.fornecedorId()));
        produto.setCriadoEm(LocalDateTime.now());

        Produto salvo = produtoRepository.save(produto);
        return paraResposta(salvo);
    }

    public List<ProdutoResponseDTO> listar() {
        List<Produto> produtos = produtoRepository.findAll();
        return produtos.stream()
                .map(produto -> paraResposta(produto))
                .toList();
    }

    public ProdutoResponseDTO buscar(Long id) {
        Produto produto = buscarOuFalhar(id);
        return paraResposta(produto);
    }

    public ProdutoResponseDTO atualizar(Long id, ProdutoRequestDTO dto) {
        Produto produto = buscarOuFalhar(id);
        produto.setNome(dto.nome());
        produto.setPreco(dto.preco());
        produto.setEstoque(dto.estoque());
        produto.setCategoria(dto.categoria());
        produto.setFornecedor(buscarFornecedorOuFalhar(dto.fornecedorId()));

        Produto salvo = produtoRepository.save(produto);
        return paraResposta(salvo);
    }

    public void excluir(Long id) {
        if (!produtoRepository.existsById(id)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Produto não encontrado");
        }
        produtoRepository.deleteById(id);
    }

    private Produto buscarOuFalhar(Long id) {
        return produtoRepository.findById(id)
                .orElseThrow(() -> new ResponseStatusException(
                        HttpStatus.NOT_FOUND, "Produto não encontrado"));
    }

    private Fornecedor buscarFornecedorOuFalhar(Long id) {
        return fornecedorRepository.findById(id)
                .orElseThrow(() -> new ResponseStatusException(
                        HttpStatus.NOT_FOUND, "Fornecedor não encontrado"));
    }

    private ProdutoResponseDTO paraResposta(Produto produto) {
        return new ProdutoResponseDTO(
                produto.getId(),
                produto.getNome(),
                produto.getPreco(),
                produto.getEstoque(),
                produto.getCategoria(),
                produto.getCriadoEm(),
                produto.getFornecedor().getId(),
                produto.getFornecedor().getNome()
        );
    }
}

    O cadastrar e o atualizar ganharam uma linha cada: buscar o fornecedor pelo número que veio no formulário e colocá-lo no produto. Se o número não existir, a resposta é 404 “Fornecedor não encontrado”, e o produto não é gravado. Esta é uma regra do segundo tipo da seção 10: precisa consultar o banco, então mora no Service.

    👨‍🏫 Com o professor · juntar as duas tabelas no SQL
    O banco também sabe seguir a ligação. Um JOIN (junção) traz o produto e o nome do fornecedor na mesma linha, comparando fornecedor_id com o id do fornecedor:
    

    psql · produto com o nome do fornecedorSQL
    SELECT p.nome, p.preco, f.nome AS fornecedor
FROM produtos p
JOIN fornecedores f ON f.id = p.fornecedor_id;
    

    O p e o f são apelidos das tabelas, para não repetir o nome inteiro. Você não precisa escrever JOIN na API: o Hibernate faz isso quando o paraResposta pede produto.getFornecedor().

    service/ClienteService.javaJava
    package com.gestorpro.api.service;

import com.gestorpro.api.dto.ClienteRequestDTO;
import com.gestorpro.api.dto.ClienteResponseDTO;
import com.gestorpro.api.model.Cliente;
import com.gestorpro.api.repository.ClienteRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.web.server.ResponseStatusException;

import java.util.List;

@Service
@RequiredArgsConstructor
public class ClienteService {

    private final ClienteRepository clienteRepository;

    public ClienteResponseDTO cadastrar(ClienteRequestDTO dto) {
        Cliente cliente = new Cliente();
        cliente.setNome(dto.nome());
        cliente.setEmail(dto.email());
        cliente.setTelefone(dto.telefone());
        cliente.setCidade(dto.cidade());

        Cliente salvo = clienteRepository.save(cliente);
        return paraResposta(salvo);
    }

    public List<ClienteResponseDTO> listar() {
        List<Cliente> clientes = clienteRepository.findAll();
        return clientes.stream()
                .map(cliente -> paraResposta(cliente))
                .toList();
    }

    public ClienteResponseDTO buscar(Long id) {
        Cliente cliente = buscarOuFalhar(id);
        return paraResposta(cliente);
    }

    public ClienteResponseDTO atualizar(Long id, ClienteRequestDTO dto) {
        Cliente cliente = buscarOuFalhar(id);
        cliente.setNome(dto.nome());
        cliente.setEmail(dto.email());
        cliente.setTelefone(dto.telefone());
        cliente.setCidade(dto.cidade());

        Cliente salvo = clienteRepository.save(cliente);
        return paraResposta(salvo);
    }

    public void excluir(Long id) {
        if (!clienteRepository.existsById(id)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Cliente não encontrado");
        }
        clienteRepository.deleteById(id);
    }

    private Cliente buscarOuFalhar(Long id) {
        return clienteRepository.findById(id)
                .orElseThrow(() -> new ResponseStatusException(
                        HttpStatus.NOT_FOUND, "Cliente não encontrado"));
    }

    private ClienteResponseDTO paraResposta(Cliente cliente) {
        return new ClienteResponseDTO(
                cliente.getId(),
                cliente.getNome(),
                cliente.getEmail(),
                cliente.getTelefone(),
                cliente.getCidade()
        );
    }
}

    BugZilla: erros previsíveis
    Mensagens reais, causa e conserto.
    

    Todos estes erros aconteceram de verdade enquanto testávamos este capítulo. Quando algo der errado, procure aqui pela mensagem ou pelo sintoma.
    

    🐛 1 · As regras estão no DTO, mas o lixo entra (201)
    Causa: falta @Valid ao lado do @RequestBody. Conserto: @RequestBody @Valid ProdutoRequestDTO dto, no POST e no PUT.
    

    🐛 2 · cannot find symbol · method getNome()
    

    Mensagem real do compiladorTexto
    error: cannot find symbol
        System.out.println(dto.getNome());
                              ^
  symbol:   method getNome()
  location: variable dto of type ProdutoRequestDTO
    

    Causa: num record, a leitura não tem get. Conserto: dto.nome(). Na entidade (com Lombok), continua produto.getNome().
    

    🐛 3 · package jakarta.validation.constraints does not exist
    Causa: a dependência de validação não está no pom.xml, ou o Maven não foi recarregado. Conserto: seção 10, passo 1.
    

    🐛 4 · Um campo volta null na resposta, sem erro nenhum
    Causa: faltou copiar esse campo no Service: num set do cadastrar ou do atualizar, ou no paraResposta. É o pior tipo de bug: nada avisa. Conserto: confira o Service campo por campo, comparando com os componentes do record.
    

    🐛 5 · O preço aparece com uma dízima enorme
    Causa: new BigDecimal(0.1), criado a partir de um double, vira 0.1000000000000000055511151231257827021181583404541015625. Conserto: crie a partir de texto, new BigDecimal("0.1").
    

    🐛 6 · illegal character: '\u2192' · ou · illegal start of expression
    

    Mensagem real do compiladorTexto
    error: illegal character: '\u2192'
        nomes.forEach(n → System.out.println(n));
                        ^
    

    Causa: a seta da lambda foi colada como o símbolo → (copiado de algum lugar que desenhava a ligadura), ou digitada como =>, a seta do JavaScript, que dá illegal start of expression. Conserto: apague e digite - seguido de >.
    

    🐛 7 · Depois do @ManyToOne, todo /produtos responde 500
    Causa: havia produtos antigos sem fornecedor, e o banco recusou criar a coluna obrigatória (o aviso contains null values no console). Conserto: pare a API, rode DELETE FROM produtos; no psql e inicie de novo. Seção 12, passo 0.
    

    🐛 8 · Excluir um fornecedor responde 500
    Causa: ele tem produtos ligados, e a chave estrangeira impede (violates foreign key constraint). Não é bug seu: é o banco protegendo os dados. Exclua ou troque o fornecedor dos produtos antes. Traduzir isso para um status melhor é uma conta para os próximos capítulos.
    

    🐛 9 · A mensagem do 404 não aparece
    Causa: falta a linha no application.properties, ou foi usado o nome antigo server.error.include-message. Conserto: spring.web.error.include-message=always e reinicie. Seção 11.
    

    🐛 10 · Funciona, mas o Controller devolve Produto em vez do DTO
    Compila e responde. Mas a conta nº 1 volta: a entidade está conversando com o mundo de novo, e qualquer campo novo da entidade passa a aparecer na resposta sem ninguém decidir. Conserto: o Controller só recebe e devolve DTOs.
