Interatividade: useState & eventos

Sua loja está linda… e parada. Hoje ela ganha memória: botões que contam, corações que curtem, uma busca que filtra em tempo real e um carrinho de verdade. Bem-vindo(a) ao hook mais famoso do React.

Eventos no React — o clique vai direto no JSX
O addEventListener do Cap 3, do jeito React
🔔 A campainha já vem instalada

No Cap 3, pra escutar um clique você tinha que achar o botão (querySelector) e instalar a campainha (addEventListener). No React, a campainha já vem de fábrica: você escreve no próprio JSX qual função toca quando o botão for clicado.

como era no Cap 3 (JS puro)JavaScript
const botao = document.querySelector("button");
botao.addEventListener("click", aumentar);
como é no ReactJSX
<button onClick={aumentar}>+1</button>
  • onClick com C maiúsculo — é o camelCase do JSX, igual ao className do Cap 4 (onclick minúsculo o React ignora de propósito).
  • Entre chaves { } — você está passando JavaScript (a função), não um texto.
  • Existe um evento pra tudo: onClick, onChange (vamos usar nos formulários), onSubmit, onMouseOver…

Num componente completo, a função fica dentro dele, antes do return:

src/App.jsxJSX
const App = () => {
  const aumentar = () => {
    console.log("clicou! 🖱️")
  }

  return <button onClick={aumentar}>+1</button>
}
⚠️
A pegadinha nº 1 do capítulo: é onClick={aumentar} — sem parênteses! Você entrega a função pro React chamar na hora do clique. Se escrever onClick={aumentar()}, os parênteses executam a função imediatamente, enquanto o React desenha a tela — antes de qualquer clique. Pense assim: você entrega a receita 📄, não o bolo pronto 🎂.
⌨️
As arrow functions => do Cap 2 vão aparecer o capítulo inteiro (inclusive no rafce, o "Rafael do Ceará"). Lembre: sua IDE pode desenhar ⇒, mas você digita = e depois > — dois caracteres.

💡 O que está faltando?

A variável até muda — o console prova. Mas o React não fica vigiando variável comum: redesenhar a tela custa caro, então ele só faz isso quando você avisa. O que a gente precisa é de uma variável especial que, ao mudar, avise o React: "ei, redesenha aí!". Ela existe — e é a estrela do capítulo. 👇

🧠
useState — a memória do componente
Seu primeiro hook: a variável que avisa o React quando muda

O let falhou porque muda em silêncio. O que a gente precisa é de uma memória que, ao mudar, avise o React. O React já entrega essa peça pronta — e ela é o seu primeiro hook.

🪝 O que é um hook?

Hook (gancho, em inglês) é uma função pronta do React que dá um poder novo ao seu componente. Você reconhece um hook de longe: o nome sempre começa com use.

O de hoje é o useState — o hook da memória, o mais usado de todos. Existem outros, e cada um vai aparecer no capítulo em que você precisar dele.

Só uma regrinha por enquanto: hook se escreve sempre no comecinho do componente, antes do return. Simples assim.

E o que o useState te dá? Uma dupla: o valor (que o React guarda por você) e a função que muda esse valor — avisando o React no mesmo instante. Exatamente o que faltava pro let.

🏟️ O placar do estádio

O gol acontece no campo, mas ninguém na arquibancada vê o número mudar sozinho: existe um operador do placar que aperta o botão, e aí sim o telão mostra 1 × 0 pra todo mundo. O useState te dá exatamente essa dupla: o placar (o valor que aparece na tela) e o botão do operador (a função que muda o valor e avisa o React pra redesenhar). Gol sem operador — o let da seção anterior — é gol que ninguém fica sabendo.

Uma linha te dá os dois. Ela parece estranha na primeira vez — vamos ler com calma:

a linha mais importante do capítuloJSX
import { useState } from "react"

const [contador, setContador] = useState(0)
const [ contador , setContador ] = useState( 0 )
contador → o VALOR (o placar que aparece na tela) setContador → a função que MUDA e avisa o React useState → o hook que cria a memória 0 → o valor INICIAL
  • O useState(0) devolve um par: o valor atual e a função de mudança. Os colchetes [ ] são a desestruturação do Cap 2 — você abre o par e dá nome às duas peças.
  • Convenção de nomes: algo e setAlgo — contador/setContador, nome/setNome, curtido/setCurtido. Todo dev React lê isso de olhos fechados.
  • O import tem chaves: import { useState } from "react" — você está pegando uma peça específica da caixa do React.

Agora o contador de verdade, completo — digite junto com o prof:

src/App.jsx — o contador clássico ✅JSX
import { useState } from "react"

const App = () => {
  const [contador, setContador] = useState(0)

  const aumentar = () => {
    setContador(contador + 1)
  }

  return (
    <div>
      <h2>Contador: {contador}</h2>
      <button onClick={aumentar}>+1</button>
    </div>
  )
}

export default App
🗣️
Leia em voz alta: "crie uma memória contador começando em 0; quando clicarem, setContador guarda o valor novo e avisa o React — que redesenha a tela com o número atualizado". Compare com a versão do let: a ÚNICA diferença é trocar a atribuição pelo set.

📜
As 3 regras do estado
Grava essas três e você escapa de 90% dos bugs

Regra 1 — só se muda estado pelo set. Atribuir direto até muda o valor… mas não avisa o React, e a tela congela (você viu na variável teimosa):

regra 1 — sempre pelo setJSX
// ❌ muda em silêncio — a tela nem fica sabendo
contador = contador + 1

// ✅ muda E avisa o React -> nova foto 📸
setContador(contador + 1)

Regra 2 — o set não é imediato. Ele encomenda a próxima foto; a foto atual continua com o valor antigo até o React re-renderizar. Por isso este clássico assusta todo iniciante:

regra 2 — a foto atual não mudaJSX
const aumentar = () => {
  setContador(contador + 1)
  console.log(contador)   // 😱 imprime o valor ANTIGO!
}
📸
Não é bug — é o modelo de fotos. O console.log roda ainda na foto atual, onde contador vale o antigo. O valor novo aparece na próxima renderização. Se um dia a tela "atrasar um clique", lembre desta regra.

Regra 3 — cada componente tem a SUA memória. Dois <Contador /> na tela = duas memórias independentes. Prove aí embaixo 👇

clique nos contadores: cada um só mexe no seu número
💡 Por que isso importa?

É o que deixa o React poderoso: o CartaoProduto pode ter um "curtir" próprio, e curtir um card não curte os outros — cada cópia do componente nasce com a sua memória zerada. Mas atenção: isso também significa que um card não enxerga a memória do outro… o que vai virar assunto na seção do carrinho. 🛒

📸 No clique, rodou setContador(5) e na linha seguinte console.log(contador). O contador valia 4. O que sai no console?
💡
Estado + porteiros = a tela que reage
Nada novo pra decorar — só juntar Cap 5 com hoje

Boa notícia: esta seção não tem NADA novo. Você vai só juntar o useState de hoje com os porteiros do Cap 5 (&& e ternário) — e é exatamente assim que nascem curtidas, abas, menus e modo escuro.

Um estado booleano (true/false) + um ternário = botão de curtir:

src/CartaoProduto.jsx — curtir ❤️JSX
const [curtido, setCurtido] = useState(false)

<button onClick={() => setCurtido(!curtido)}>
  {curtido ? "❤️ Curtido" : "🤍 Curtir"}
</button>
🔀
O !curtido é o "NÃO" do Cap 2: transforma true em false e vice-versa. setCurtido(!curtido) = "vira a chavinha". É O padrão pra qualquer botão liga/desliga.

E um booleano + o porteiro && = mostrar/esconder qualquer coisa:

mostrar detalhes só quando pedirem 👻JSX
const [mostrar, setMostrar] = useState(false)

<button onClick={() => setMostrar(!mostrar)}>ver detalhes</button>
{mostrar && <p>Entrega em 5 dias úteis 🚚</p>}
🧩 A fórmula mágica do React

tela = f(estado). Você não "manda mostrar/esconder" como no Cap 3 (style.display…). Você só muda o estado — e o JSX, com seus porteiros, desenha a tela certa pra aquele estado. O React faz o resto.

Formulários controlados — o input com crachá
Cada tecla passa pelo estado (e é assim que nasce a busca)
🪞 O input-espelho

No HTML puro, o input guarda o texto sozinho e você só descobre o valor quando pergunta. Em React a gente inverte: o estado é o dono do texto, e o input vira um espelho dele. Cada tecla dispara o onChange, que guarda a letra no estado; o estado muda → nova foto 📸 → o input mostra o texto atualizado. Parece burocracia, mas te dá superpoderes: validar, limpar, filtrar e reagir a cada tecla.

src/App.jsx — input controladoJSX
const [nome, setNome] = useState("")

<input
  value={nome}
  onChange={(e) => setNome(e.target.value)}
  placeholder="Digite seu nome"
/>
<p>Olá, {nome}! 👋</p>
  • value={nome} — o input mostra o que está no estado (o espelho).
  • onChange={(e) => ...} — a cada tecla, o evento dispara. O e é o mesmo objeto-evento do Cap 3.
  • e.target.value — "do evento, pegue o elemento-alvo, e dele o texto atual". Decore o trio: vai digitá-lo mil vezes.

Digite no espelho e veja o estado acompanhar cada tecla. Depois aperte tirar o onChange e tente digitar… 👇

// cada tecla dispara o onChange…
o input é o espelho; o estado é o dono do texto

Sentiu? value sem onChange = campo congelado: o espelho mostra o estado, mas ninguém atualiza o estado — então digitar não faz nada (e o React ainda reclama no console). Os dois andam sempre juntos.

O estado mora no pai — o segredo do carrinho
Quando VÁRIOS componentes precisam do mesmo dado
🏠 A geladeira fica na cozinha

Pensa no total do carrinho: o botão "Adicionar" fica no CartaoProduto, mas o numerozinho 🛒 aparece no Cabecalho. Se cada card tivesse o próprio contador (regra 3!), o cabeçalho nunca ficaria sabendo. A solução da família React: o que é de todos fica no cômodo comum — o estado mora no pai (App), que é pai do Cabecalho E dos cards.

App aqui mora carrinho + aoComprar
⬇ dados descem (props)⬆ avisos sobem (função)

💡 Repare: função também é prop!

O aoComprar desce pro filho igualzinho a nome ou preco — só que o valor é uma função. O filho não sabe (nem precisa saber) o que ela faz: ele só toca a campainha no clique, e quem atende é o pai. Dados descem ⬇, avisos sobem ⬆. Você vai reusar esse desenho no Cap 9, no ERP.

🧭
Regra de bolso pra decidir onde o estado mora: "quem precisa ver esse dado?" Só um componente → o estado fica nele (o curtir ❤️). Vários → o estado sobe pro pai comum mais próximo (o carrinho 🛒).

BugZilla ataca o estado!
Os 5 tropeços clássicos do useState
🐛
Bug 1 — mudou o estado na mão: contador = contador + 1. O pior tipo de bug: nem dá erro — a tela só congela. Conserto: estado só muda pelo set: setContador(contador + 1).
🐛
Bug 2 — parênteses no onClick: onClick={aumentar()} executa na renderização. E se aumentar tem um set dentro, vira um loop: renderiza → executa → set → renderiza → executa… ("Too many re-renders"). Conserto: sem parênteses (onClick={aumentar}) ou embrulhado (onClick={() => aumentar(2)}). Guarde esse loop — ele volta no Cap 7!
🐛
Bug 3 — esqueceu o import: "useState is not defined". Conserto: import { useState } from "react" no topo — com chaves no useState, que você está pegando uma peça específica da caixa.
🐛
Bug 4 — input com value e sem onChange: o campo congela (você digita e nada acontece) e o console mostra o warning "You provided a `value` prop to a form field without an `onChange` handler". Conserto: espelho completo — value={nome} e onChange={(e) => setNome(e.target.value)}.
🐛
Bug 5 — esperar o set na mesma linha: setContador(5) e logo abaixo console.log(contador) mostra o antigo. Não é bug do React — é a regra 2 (o set encomenda a próxima foto). Conserto: use o valor que você acabou de calcular (const novo = contador + 1) ou confie na próxima renderização.
👀 Macete de ouro do BugZilla▼
🔦
Tela congelada? Pergunte na ordem: 1) estou mudando pelo set? 2) o onClick está sem parênteses? 3) o useState está importado? E leia o console: "Too many re-renders" = parênteses no onClick; warning de value = faltou o onChange. O erro sempre deixa bilhete.

O que você leva deste capítulo
Sua loja agora REAGE — e você entende por quê
  • Eventos: onClick={funcao} — camelCase, entre chaves e sem parênteses (a receita, não o bolo). Com valor: onClick={() => funcao(x)}.
  • useState: const [valor, setValor] = useState(inicial) — a memória que avisa o React. Nomes sempre algo/setAlgo.
  • O ciclo: clique → set → React re-renderiza (nova foto 📸) → tela nova. E as 3 regras: só pelo set · o set não é imediato · cada componente tem a sua memória.
  • Formulário controlado: value={x} + onChange={(e) => setX(e.target.value)} — o estado é o dono do texto.
  • O estado mora no pai quando vários componentes precisam dele: dados descem como prop ⬇, avisos sobem como função ⬆.
